## 확정 규칙

### R1. 사용 주체 (usage_subject)

신뢰정책 판정(`principal_kind`)은 **그대로 두고** 실사용 축을 따로 만든다. 두 값은 다른 사실이다 —
"누가 집을 수 있나" vs "실제로 누가 집었나". 최종 판정은 둘의 논리합.

양성 근거만 승격한다. **부재는 판정 근거가 아니다.** 우선순위:

| 순위 | 근거 | 판정 |
|---|---|---|
| 1 | IAM 사용자다 | human |
| 2 | 세션에 MFA 인증 표시가 있다 | human |
| 3 | AssumeRole 호출자가 IAM 사용자 / 페더레이션 / SSO 다 | human |
| 4 | 신뢰정책 `Principal.AWS` 가 IAM 사용자 ARN 이다 | human |
| 5 | 이벤트에 서비스 호출 표시(`invokedBy`)가 있다 | machine |
| 6 | 세션 이름이 자동화 형식이다 | machine |
| 7 | 신뢰정책이 AWS 서비스를 가리킨다 | machine |
| — | 아무 근거 없음 | none (사유 구분) |

MFA 표시가 **없는 것**은 사람이 아니라는 근거가 못 된다(IdC 콘솔 세션도 없을 수 있다). 4·7 만 신뢰
정책 유래이고 나머지는 CloudTrail 유래다.

**분류는 저장하지 않고 run 마다 재도출한다.** 사람이 화면에서 수정한 값만 도구 소유 저장소에 남는다.

#### R1-a. 세션 이름 원문은 산출물에 저장하지 않는다 (AppSec)

SSO 는 **세션 이름에 사용자 이메일**을 쓴다. 자동화 세션 이름에는 계정 ID 가 박힌다. 사람 판정의
핵심 근거가 개인정보라는 뜻이다. 따라서:

- 세션 이름은 **판정에만 쓰고 원문을 산출물·정규화 데이터에 남기지 않는다.**
- 남기는 것은 분류 결과뿐. 열린 문자열이 아니라 **닫힌 라벨 집합**이다(`email_like` /
  `account_id_embedded` / `uuid_suffix` / `service_name` / `other`) — 열린 `str` 이면 구현 실수 한
  번에 원문이 새어 나가고, S3 에 쓰인 다음에는 되돌릴 수 없다. `PrincipalRecord` 는
  `validate_assignment` 로 **대입 시점에** 거부한다(이 모델은 단계별로 채워지므로 생성 시점 검증만
  으로는 늦다). 라벨을 늘릴 때는 "이 라벨로 원문을 재구성할 수 있나" 를 먼저 답할 것.
- 근거 문장도 원문을 노출하지 않는다. "세션 이름이 이메일 형식" 까지만.
- 테스트로 강제한다(산출물 전문에 `@` 를 포함한 세션 문자열·12자리 계정 ID 부재 어서션).

### R2. 미사용 일수와 등급

```
미사용 일수 = ① 활동 기록(AWS 가 역할마다 보관하는 마지막 활동 시각)이 있으면 그 날짜부터
              ② 없으면 생성일부터
```

**① 에는 상한을 두지 않는다.** AWS 문서상 추적 보장은 400일이지만 실측에서 1,076일 전 날짜가 그대로
나왔다 — AWS 가 기록한 사실이므로 그대로 쓴다. **400일 문구는 ② 에만 붙는다.**

| 경우 | 화면 표기 |
|---|---|
| ① | `1,076일 미사용 (마지막 활동 2023-09-20, us-east-1)` |
| ② | `생성 후 1,076일 · 사용 기록 없음 (AWS 추적 보장 400일)` |

활동 기록은 **전 리전**을 통틀어 준다 — 수집 리전 밖의 활동을 놓치지 않는 유일한 근거다.

등급 경계는 config. 기본값 30/60/90.

| 등급 | 기준 |
|---|---|
| active | 29일 이하 |
| watch | 30~59일 |
| review | 60~89일 |
| cleanup | **90일 이상** |
| new | 생성 후 30일 미만 → 등급 유보 |

**권한(action) 단위 등급**: 미사용 action 에는 마지막 사용일이 정의상 없다. 그 **서비스**를 마지막으로
사용한 날을 하한선으로 쓴다(서비스를 200일 안 썼으면 그 안의 어떤 권한도 200일 안 쓰였다). 서비스를
어제 썼으면 하한선이 1일이라 아무 말도 못 한다 → **판정 불가 유지**. 서비스 사용 기록이 아예 없으면
최상위 등급.

함정을 '판정 불가' 분리 때 이미 한 번 겪었다.

### R4. 와일드카드

`*` 를 gap 계산에서 빼는 것은 유지한다(부여 범위에 상한이 없어 미사용 개수를 셀 수 **없다**). 대신
**와일드카드 보유 사실 자체를 findings 로 승격**한다.

- 신규 유형 `wildcard_grant`, 위험도 규칙에 가중치 추가(config)
- 트랙과 무관하게 목록 최상단 + 배너
- 권고 문구는 "미사용 N개 제거" 가 아니라 **"실사용 기반 재작성"**
- 정책 초안은 실사용 권한만으로 생성

**신뢰정책 와일드카드는 별 항목이다.** `Principal: "*"` 이거나 조건 없이 광범위한 신뢰는 범위 판정
문제가 아니라 그 자체가 보안 결함이다. 신규 유형 `trust_policy_wildcard` 로 트랙과 무관하게 올린다.

### R5. 테넌트 그룹 — "우리 계정" 의 정의

배포 계정도, 조직도 기준이 아니다. 배포 계정은 도구가 어디 사는지일 뿐이고, 조직은 코드에 개념
자체가 없다(`config.py` 에 명시 계정 목록만 있고 Organizations 호출 0건).

그리고 **`config.accounts` 전체를 "우리" 로 볼 수도 없다.** 이 도구는 여러 고객의 계정을 한 배포에서
관리하는 형태로 쓰인다(중앙 배포 + config 에 전 고객 계정). 그 경우 A 고객 계정의 역할이 B 고객
계정을 신뢰하면 "내부라 안전" 이 아니라 **테넌트 경계 위반**이다.

그래서 config 에 **테넌트 그룹**을 도입한다. 하위호환을 위해 문자열 목록도 계속 받는다(= 단일 그룹).

```yaml
accounts:
  - { id: "1111…", group: "customerA" }
  - { id: "2222…", group: "customerA" }
  - { id: "3333…", group: "customerB" }
# 문자열 목록도 유효 — 전부 기본 그룹으로 묶인다.
```

판정은 "외부인가?" 를 묻지 않고 **"내부라고 확인됐나?"** 를 묻는다. 오판의 비대칭 때문이다 —
외부(벤더) 역할을 내부로 오판하면 삭제 권고에 올라가 고객이 벤더 연동을 끊는다. 내부를 외부로
오판하면 "소유자 확인" 으로 한 단계 밀릴 뿐이다. **모르면 보수적으로.**

| 신뢰 대상 | `trust_scope` | 배정 |
|---|---|---|
| **같은 그룹** 계정 | `internal` | 삭제 검토 가능 |
| **다른 그룹** 계정(수집 대상이지만 다른 고객) | `cross_tenant` | 🔴 **테넌트 경계 위반 의심** — 신규 findings, 삭제 검토 아님 |
| 도구가 사는 관리 계정 | `tooling` | 정상 운영 경로. 라벨만, 조치 없음 |
| AWS 서비스 | `service` | 트랙② |
| 어디에도 없음 | `unconfirmed` | 소유자 확인 트랙(③-b) |

`cross_tenant` 는 이 도구가 스스로 찾기 가장 어려운 종류의 문제를 잡아 준다.

**Organizations 조회는 이번 범위에서 뺀다.** 관리 계정·위임 관리자에서만 되고, 그룹 선언(위 config)이
같은 정보를 추가 권한 없이 준다. 필요하다고 확인된 다음에 넣는다.

### R5-b. 트랙 배정

수집 대상은 계정의 **IAM 사용자 전부 + 역할 전부**. 아무도 처음부터 빼지 않는다.

```
90일 이상 미사용?
   ├─ 예 → 신뢰 대상이 우리 테넌트로 확인됐나?(trust_scope)
   │        ├─ 아니오(unconfirmed) → 트랙③-b  외부 연동 · 소유자 확인 필요 (삭제 권고 안 함)
   │        └─ 예(internal) → 트랙③  삭제 검토 (정책 초안 없음)
   └─ 아니오 → 누가 쓰나?
            ├─ 사람 → 트랙①  Persona (여러 대상을 묶어 공통 정책 1개)
            └─ 기계 → 트랙②  서비스 역할 (역할별 개별 정책, 절대 묶지 않음)
```

**우선순위: 90일 이상 미사용이면 트랙③ 이 이긴다.** 지울 대상의 정책을 다듬는 것은 낭비다.

**트랙② 를 묶지 않는 이유**: Lambda 실행 역할 둘을 한 정책으로 묶으면 서로의 권한을 얻는다 —
최소권한의 반대다.

**트랙③ 에 정책 초안을 주지 않는 이유**: 사용 기록 0 이면 빈 정책이 나온다. 빈 정책은 "지워도 된다"
거나 "관측 기간 밖에서 쓰이고 있다" 둘 중 하나고, 후자면 적용 순간 장애다.

**트랙③-b 를 가르는 이유**: 실측에서 90일 이상 미사용 역할의 다수가 **다른 도구·벤더가 심어놓은
역할**이었다(감사 도구, 백업 SaaS, 보안 스캐너). 안 쓰이는 게 정상인 역할이다. 삭제 권고에 하나라도
위험한 것을 섞으면 고객이 목록 전체를 안 믿는다 — 이 목록의 가치는 개수가 아니라 신뢰다.

### R8. persona 군집이 계정·테넌트 경계를 무시한다 (신규 발견, 필수 수정)

`m5_catalog.py:190` `_cluster_key` 는 (도메인 × 성격) 만 쓴다. 계정을 보지 않는다. `CatalogEntry` 에
계정 필드가 없고 `/catalog` 엔드포인트도 계정 파라미터를 받지 않는다 — persona 는 **전역**이다.

단일 고객 배포에서는 문제가 아니었다(계정이 다 같은 고객 것). 여러 고객을 한 배포에서 관리하면 셋이
동시에 깨진다.

1. **정확성** — A 고객 정책이 B 고객 사용 실태에서 파생된다.
2. **정보 유출** — A 고객에게 주는 산출물(정책·Terraform·리포트)에 **B 고객 계정 ARN 이 들어간다.**
3. **적용 범위** — Permission Set 하나가 여러 테넌트에 걸릴 수 있다.

화면 필터를 붙이는 것으로는 해결되지 않는다. 표시를 걸러도 **정책 내용은 합쳐진 상태** 그대로다.

→ **군집 키에 테넌트 그룹을 축으로 추가한다.** 산출물 파일명·경로도 그룹으로 분리한다.

범위는 크지 않다. 지표·리포트·principal 목록·정리 백로그는 **이미 계정 축을 갖고 있다** — 그래서
트랙②·③ 은 기존 구조를 따라가면 자동으로 분리된다. 격리가 필요한 것은 persona 와 그 파생 산출물뿐
이다. P4 에 함께 넣는다.

### R6. 제외 대상 — 개수는 화면에 남긴다

조용히 사라지는 것이 없어야 한다. "왜 우리 역할이 여기 없지?" 에 답할 수 있어야 한다.

| 제외 | 이유 |
|---|---|
| AWS 관리 service-linked 역할 | AWS 소유. 사람이 손댈 수 없다 |
| 배포 도구 부트스트랩 역할(config 패턴) | 고치면 배포가 깨진다 |
| 생성 후 30일 미만 | 관측 기간 자체가 짧다 |
| **도구 자신의 읽기 전용 역할** | 모든 대상 계정에 존재하고 관리 계정을 신뢰한다. 계정 수만큼 노이즈가 늘어난다. 검증 계정에서 실제로 "판별 불가" 로 persona 목록에 올라와 있었다 |

### R7. 규모 문제 — 트랙② 를 어떻게 보여주나

권한을 하나씩 뿌리면 3,000줄이 된다. 안 뿌리는 것과 같다. **권한을 세지 말고 결정을 센다.**

1. **서비스(namespace) 단위로 접는다.** 권한 이름은 `서비스:동작` 이다. 앞부분으로 묶으면 실측
   14,732 → 2,669 행. 여기서 "인증 이력이 전혀 없는 서비스" 를 한 덩어리로 묶으면 **결정 332건**.
   부여 3,093 / 317 서비스 / 사용한 서비스 0 인 역할은 **결정 1건**("317개 서비스 전부 제거").
2. **부여 권한 집합이 동일한 역할을 한 행으로 접는다.** 실측 84 역할 → 49 그룹.
3. **등급 필터 기본 ON**(cleanup 만) → 첫 화면 수십 줄.

화면은 3층. 1층 대시보드에 숫자 하나(정리 권고 N건), 2층 목록(역할·등급·일수·줄일 서비스 수),
3층에서 처음 서비스 접기 화면. **정책 파일 본문은 화면에 렌더하지 않고 다운로드만.**

트랙② 전용 상시 경고: 기계 역할의 권한 축소는 장애 직결이다("적용 전 스테이징 검증. 관측 기간이
짧은 계정은 기간 밖 사용이 있을 수 있음"). 관측 기간이 30일 미만이면 경고를 빨간 띠로 승격.

**노출 조건**: 위 1·2·3 이 실측으로 목표치에 도달하면 화면을 낸다. 도달하지 못하면 이번에는
리포트·백로그 텍스트로만 내고 탭을 만들지 않는다. 정리되지 않은 수천 줄을 보여주는 것은 안 보여주는
것보다 나쁘다.

현행 행은 `{principal, event_source, event_name, count, last_used}` 만 남기고 **누가 집었는지를 버린다**.

### 신규 산출물 (트랙②)

- `ServiceRollup`: `{namespace, granted_count, used_count, last_used, tier, verdict: keep|remove|undetermined}`

### config 신규 키

`risk_rules` 안에 `unused_tier_days: [30, 60, 90]` · `unused_role_days: 90` ·
`new_principal_days: 30` · `weight_trust_policy_wildcard: 30`. 임계치를 이미 `long_lived_key_days` ·
`unused_action_days` 가 사는 곳에 함께 두는 이유는 "무엇이 미사용인가" 의 출처가 두 곳으로 갈라지지
않게 하기 위해서다. `unused_tier_days` 는 **서로 다른 값의 오름차순**을 강제한다(아니면 도달 불가
등급이 생긴다). granted 와일드카드 가중치는 `weight_wildcard_action` 으로 이미 있다.

`accounts` 항목에 `group`(R5). 로더가 **계정 ID 목록으로 정규화**하고 그룹은 파생 필드
`account_groups`(id→group)로 낸다 → 계정을 순회하는 기존 코드는 변경 0. 문자열 목록도 계속 받아
기존 고객 config 는 안 깨진다(전부 `default` 그룹). 범위 밖 계정 조회는 `""`(모른다)이며 기본 그룹을
주지 않는다 — 그러면 신뢰정책이 가리키는 남의 계정까지 internal 이 되어 fail-safe 가 뒤집힌다.

**임계치·계정 리터럴은 config 에만**(불변식 ④).

`exclude_service_roles` 의 의미가 바뀐다: "버린다" → "persona 묶음에서 빼고 트랙② 로 보낸다".
키 이름은 호환을 위해 유지하되 주석과 문서를 고친다.

**사용 실태가 달라** 등급·미사용 일수·줄일 서비스 수가 역할마다 다르다. 한 행으로 합치면 그 행의 숫자는
어느 역할에도 해당하지 않는 조작된 값이 된다(목데이터의 `lambda-invoice-exec` cleanup/97일 과
`lambda-refund-exec` active/3일 이 같은 `group_key` 다). 대신 `부여 집합` 칼럼에 `+N개 동일` 을 두고
Popover 에서 형제 역할의 등급·줄일 서비스 수를 각각 보여주고, **정책은 역할별로 따로 적용해야 한다**는
이유를 그 자리에서 말한다. P4 가 이 접기를 152→107(표시용·약함)로 이미 기록했고 P6 를 막지 않는다고
판정한 대로다.

**결정 사항 2건:**

1. `OBSERVED_MIN_DAYS = 30`(`ServiceRoles.tsx:43`)은 **설계 상수이며 config 임계치가 아니다.** 관측 구간은
   고객이 정하는 값이 아니라 CloudTrail 이 실제로 덮은 사실이고, 이 값은 "이 정도면 경고를 빨간 띠로
   승격한다"는 화면의 판단이다. config 로 빼면 고객이 경고를 낮출 수 있게 된다.
2. **정책 본문은 렌더하지 않는다.** 상세 화면은 결정 목록만 보여주고 본문은 `결정 CSV` 로만 내려간다.
   CSV 주입 방어·BOM·인용 규칙은 새 `lib/csv.ts` 한 곳에 두고 `CleanupBacklog` 도 그것을 쓰게 바꿨다 —
   두 벌이 되면 한쪽만 고쳐지고, CSV 는 화면에서 검증되지 않는 산출물이라 그 사실을 아무도 모른다.

**판별력 확보(= "항상 빨간 띠" 가 통과하지 못하게).** 목데이터를 양쪽 상태가 다 나오게 만들었다:
계정 `111122223333` 은 관측 구간이 전부 30일 이상(최소 45일) → **warning**, 전체 계정에는 12일과 `null`
이 섞여 → **error**. 렌더 검사는 문구뿐 아니라 Alert 의 `awsui_type-error` / `awsui_type-warning`
**클래스**를 보고, 계정을 좁힌 뒤에는 승격 문구가 **사라져야** 한다고 `notExpect` 로 못 박았다. 등급 필터도
같은 방식이다(cleanup 기본값에서 `config-recorder-helper`·`api-gateway-authorizer` 부재를 요구).

**1층 숫자의 출처.** 대시보드 KPI `서비스 역할 정리 권고` 는 M5 산출물의 `decision_count` 합이며 지표에서
다시 계산하지 않는다 — 접기 규칙이 두 곳에 생기면 화면과 상세가 어긋난다. 조회 실패는 `0` 이 아니라 `—`
로 렌더하고 "0 이 아니라 미확인" 이라고 쓴다.

**렌더로 확인하지 못한 경로:**

- **실 API 모드**(`VITE_USE_MOCKS=false`)로 이 화면을 띄운 적이 없다. 백엔드 경로는 있고
  (`backend/lp2ps_api/repositories.py:304`) 타입은 맞지만, **라이브 실증은 미실시**다.
- 실 산출물에는 `observed_days` 가 아직 없다(필드 추가 전에 생성된 파일이라 전부 `null`).
  `normalized.parquet` 에서 152 service_role principal 의 `observed_days` 가 모두 0 인 것은 확인했으므로
  라이브에서는 빨간 띠가 뜰 것으로 보이지만, **화면으로 확인한 것은 아니다.**
- 최대 규모 상세(서비스 행 195 · 결정 66건)를 실제로 렌더한 적 없다. 목데이터의 최대는 그보다 훨씬 작다.

### P7 완료 (트랙③ / ③-b 백로그 반영 — 외부 연동이 삭제 권고에 섞이지 않음)

**엔진**: 미사용 90일 이상 역할이 `unused_role`(삭제 권고) / `unconfirmed_trust_role`(소유자 확인)로
갈린다(`m6_reporter.py:381`). 판정은 `is_deletion_reviewable` 단일 함수이고 `m5_tracks` 가 **그것을
import 한다**(`m5_tracks.py:81`) — 트랙 배정과 백로그 문구가 각자 판정하면 "화면은 소유자 확인,
백로그는 역할 삭제" 가 생긴다. 이 리포는 같은 종류의 어긋남(대시보드 40 vs 백로그 59)을 이미 겪었다.
`cross_tenant_trust` 는 **미사용 여부·트랙과 무관하게** 별 항목으로 나간다(`m6_reporter.py:507`).

**지표**: `unused_roles` 정의는 **바꾸지 않았다**(`definition_version` 유지 — 정의를 또 바꾸면 추이
비교가 다시 끊긴다). 대신 `owner_review_roles` 를 추가해 산술을 닫았다:
`백로그 unused_role 건수 = unused_roles - owner_review_roles`. 이 산술을 테스트로 고정했다
(`test_owner_review_metric_reconciles_with_the_backlog`).

**화면**: 대시보드 KPI 힌트가 그 산술을 문장으로 말하고(`Dashboard.tsx:449`), 백로그는 신뢰 축 배너 +
`cross_tenant_trust` 카드 고정(`pinRank`) + 드릴다운 유형별 경고를 낸다. 두 유형 화면에는 삭제 권고
문구가 **하나도** 없다.

넣고 `too_new` 만 예외로 통과시켰다(그 사유는 `new_role_unused` 와 같은 사실을 말한다). 정의 변경이

**목데이터로는 나올 수 없었던 이유**: 목데이터에는 제외 대상이면서 90일+ 미사용인 레코드가 없었다.
즉 P7 의 "22스텝 ALL PASS" 는 이 결함에 대해 **통과가 아니라 미측정**이었다.

  **`0` 으로 그려진다.** 힌트 문구는 "0 이 아니라 산정 불가" 라고 말하는데 숫자는 0 이다. 판단 필요.

2. **정의 변경으로 추이가 단절된다.** R3 의 정의 버전 표시가 누락되면 오독이 확정적이다.

   CloudTrail(짧음)을 같은 등급으로 합치지 않는다 — CloudTrail 은 "썼다" 의 양성 근거로만 쓴다.
   관측 기간 30일 미만이면 목록 상단에 상시 경고 띠.
4. **트랙② 가 정리되지 않으면 내지 않는다.** P4 목표치 미달 시 P6 을 버린다.
